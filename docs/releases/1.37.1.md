# Observador 1.37.1 — identidad de ofertas y cierres pendientes

Base de desarrollo: `ca1c7c3` (1.37.0), rama `sectores-cerrar`.
Versión de aplicación: **1.37.1 / 47**. Estructura de datos: **Room 14**, sin migración.

## Problema y comportamiento resultante

Las cifras de dos ofertas pueden ser iguales. Antes, el enlace por precio/km/min podía marcar ambas como tomadas o hacer que el análisis tomara el resultado de un viaje distinto. La lectura usa ahora dos identidades: una huella SHA-256 del contenido normalizado y un identificador `OFFER-V2-…` por aparición. El identificador se almacena en las columnas de enlace lógico ya existentes.

- Los repintados conservan ID y fecha de detección inicial.
- El Radar conserva IDs al reordenar tarjetas distintas. Tarjetas idénticas simultáneas reciben IDs separados, pero su aceptación y cierre se consideran ambiguos.
- Una ausencia confirmada de 1,5 segundos, contada desde la primera lectura sin tarjeta, o un cambio de ventana inicia otra aparición.
- Tras perder/reiniciar completamente el servicio, la lectura inicia nuevas apariciones; no se reconstruye una continuidad que no fue observada.
- El viaje solo copia ofertas detectadas antes de su evento. La oferta se encola antes que los eventos que necesitan copiarla.
- Si hay varias tarjetas y no se sabe cuál se aceptó, el viaje no se atribuye a la primera.
- Los enlaces anteriores requieren la huella guardada y la fecha exacta de su snapshot. Conflictos conservan el viaje como fila propia. Las filas sintéticas tienen IDs negativos estables y resolución de colisiones; dos horas de fin iguales no eliminan un viaje.
- Análisis usa el mismo enlace de apariciones que Inicio/Reportes. El modelo en sombra solo usa una evaluación heredada si el intervalo entre detección y aceptación identifica un único viaje.

## Cierres pendientes

La configuración de cierre se lee de un único snapshot de DataStore. Cada solicitud conserva la revisión de configuración, aparición, contenido y ventana. Se invalida al cambiar de modo, pausa, sectores, visibilidad o ventana. Tocar la tarjeta también impide que un procesamiento asíncrono todavía sin programar reactive el cierre.

Antes de ejecutar se vuelven a leer los ajustes y la pantalla, se exige Uber al frente y una tarjeta flotante visible para cancelar, y se verifica el contenido completo y la X única. Se rehúsa actuar si otra tarjeta tiene el mismo precio. Los nodos y todas las raíces adquiridas se liberan incluso en las salidas tempranas.

El límite diario usa una reserva persistente anterior al toque, incluyendo cierres heredados; un error al leer/escribir el presupuesto impide nuevos intentos. Un intento real fallido o no verificado consume igualmente su cupo. Android aceptar el comando solo registra `TOQUE SOLICITADO`; `CERRADA` requiere una lectura posterior que compruebe que la tarjeta desapareció en una pantalla reconocible.

**El toque real permanece desactivado.** `CloseTarget.VALIDATED = false`. Las ramas que realizan o comprueban toques necesitan validación física futura; las pruebas de esta entrega no constituyen validación de la X de Uber.
